Dhole {{ .Chart.AppVersion }} is installed as {{ include "dhole.fullname" . }}.

The API has no unauthenticated call. The control plane mints a bootstrap
service token at start-up, prints it once, and writes it to
/var/lib/dhole/bootstrap.token:

  kubectl -n {{ .Release.Namespace }} logs deploy/{{ include "dhole.fullname" . }} | head -3

Reach the contract:

  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "dhole.fullname" . }} {{ .Values.service.port }}:{{ .Values.service.port }}
  export DHOLE_SERVER=http://127.0.0.1:{{ .Values.service.port }}
  export DHOLE_TOKEN=<the token from the log above>
  dhole pipeline validate --file pipeline.yaml

A revision may not be approved by its author, and the bootstrap credential is
the only one a fresh install has — so it can write a pipeline and nothing can
run it until a second principal exists. Mint one against the plane's own
database, which is what the bootstrap credential is for:

  kubectl -n {{ .Release.Namespace }} exec deploy/{{ include "dhole.fullname" . }} -- \
    /ko-app/dhole token issue --subject reviewer --store-dsn "$DSN"

where $DSN is the value in the {{ include "dhole.storeSecretName" . }} Secret. The
image has no shell, so this runs the binary directly rather than through one.

WARNING: objectStore.kind is not s3, so every process keeps its own object
store. An engine writes a step's log and outputs to its own pod's disk, and the
control plane looks for them on its own and does not find them. Nothing errors:
every step succeeds and everything it produced is unreachable. Set
objectStore.kind=s3 for any deployment whose engines are not in the control
plane's own pod.
